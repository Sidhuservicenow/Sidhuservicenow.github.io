01. Troubleshooting Approach

When an integration fails, avoid immediately changing roles, credentials or configurations. First identify which integration layer is failing.

Connector

Can Moveworks authenticate and communicate with ServiceNow?

Identity

Are users imported and correctly matched across systems?

Authorization

Does the integration account have the required permissions?

Functionality

Does the intended knowledge, ticketing or catalog capability work?

Recommended investigation sequence

  1. Capture the exact error message and timestamp.
  2. Identify the affected user and operation.
  3. Check Moveworks connector status.
  4. Review ServiceNow authentication and transaction logs.
  5. Validate account roles and access controls.
  6. Reproduce the issue in a controlled test environment.
  7. Document the root cause and verified resolution.
Developer tip: Separate connectivity, authentication, authorization, identity mapping and business logic. A successful connector test does not prove that all downstream functionality works.

02. HTTP Error Investigation

HTTP status codes are useful diagnostic signals. The following table describes general HTTP meanings, not guaranteed Moveworks-specific error messages.

Status General meaning Investigation
400 Bad Request Inspect request parameters, query syntax and payload.
401 Unauthorized Check credentials, authentication method and token validity.
403 Forbidden Check roles, ACLs, scopes and record permissions.
404 Not Found Check endpoint, table name, record ID and instance URL.
405 Method Not Allowed Verify whether the endpoint supports the HTTP method.
429 Too Many Requests Investigate rate limits and request frequency.
500 Internal Server Error Inspect server-side logs and application errors.
502 / 503 / 504 Gateway or availability errors Check service availability, network and upstream timeouts.
Do not assume that every 401 or 403 originates from ServiceNow. Determine which component generated the response before changing configuration.

03. Authentication Failures

Scenario: The ServiceNow connector test fails with an authentication error.

Possible causes

  • Incorrect integration account credentials.
  • Inactive or locked ServiceNow account.
  • Authentication method mismatch.
  • Missing API access permissions.
  • OAuth token or credential configuration problems.

Investigation steps

  1. Open the ServiceNow integration account.
  2. Verify that the account is active.
  3. Confirm the configured authentication method.
  4. Check the account's required roles.
  5. Test the approved API endpoint independently.
  6. Review the connector's latest error details.

Example REST API connectivity test

GET https://YOUR_INSTANCE.service-now.com/api/now/table/sys_user?sysparm_limit=1

Accept: application/json

Use an approved API client and the same authentication method configured for the connector. This example tests basic API access; it does not reproduce the entire Moveworks integration flow.

Expected investigation result: Confirm whether the API request succeeds and whether the integration account can access the requested resource.

04. User Identity Ingestion Issues

Scenario: The connector works, but users are missing from the Moveworks user roster.

Possible causes

  • Incorrect identity source configuration.
  • Incorrect joining key.
  • Missing or duplicate email addresses.
  • Incorrect active-user filter.
  • Connector cannot read ServiceNow user records.
  • Identity validation failures.

Example ServiceNow user query

GET /api/now/table/sys_user

Query:
active=true^emailISNOTEMPTY

Parameters:
sysparm_limit=10
sysparm_fields=sys_id,user_name,email,active

This is an example diagnostic query. Confirm the actual filter and joining key configured in your Moveworks tenant.

Validation checklist

  • Verify the user exists in ServiceNow.
  • Check that the user is active.
  • Confirm the email is populated.
  • Check that the joining key matches the configured source.
  • Inspect duplicate or dropped records.
  • Review user ingestion logs.
Moveworks identity ingestion uses joining keys to match records. A duplicate Unique Record ID can cause a record to be dropped. Investigate the roster and joining-key configuration before changing the source data.

05. Bot Account Configuration Problems

Scenario: User ingestion is configured, but automated actions fail because the Bot Account cannot be mapped correctly.

Verify these fields

Field What to verify
Email Address Matches the integration account email.
Unique Record ID Matches the identity joining key and is unique.
External ID Matches the ServiceNow account sys_id.
ITSM User ID Matches the ServiceNow user ID.
Integration ID Matches the configured connector name.

Investigation procedure

  1. Open the integration account in ServiceNow.
  2. Copy its email, user ID and sys_id.
  3. Open Moveworks Bot Account settings.
  4. Compare each corresponding field.
  5. Validate the connector association.
  6. Run the relevant identity and action tests.
Never copy production credentials or actual account identifiers into public troubleshooting articles. Use placeholders in examples.

06. Knowledge Search Issues

Scenario: An employee asks a question, but the assistant does not return an expected ServiceNow knowledge article.

Possible causes

  • Knowledge Search has not been configured.
  • The article is not published.
  • The integration account cannot read the knowledge base.
  • User criteria prevent access.
  • Permission mirroring is not working.
  • Initial ingestion or incremental synchronization is incomplete.

Investigation procedure

  1. Verify that ServiceNow Knowledge Search is configured.
  2. Check whether the article is published.
  3. Verify the knowledge base permissions.
  4. Check whether the integration account can read the article.
  5. Validate Moveworks ACL update set installation.
  6. Review ingestion validation and error summaries.
  7. Test the article with an authorized employee account.
Moveworks documents an initial content-and-permissions ingestion window of approximately 12 hours for its Assistant Platform knowledge setup. Subsequent incremental syncs are documented at 15–30 minute intervals. Check your tenant's current ingestion status before concluding that an article is missing permanently.

07. Access and ACL Problems

Scenario: The integration account can authenticate, but a particular table or record cannot be accessed.

What to investigate

  • Table-level read or write ACLs.
  • Field-level ACLs.
  • Required ServiceNow roles.
  • Record-level restrictions.
  • Knowledge user criteria.
  • Catalog item user criteria.
  • Domain separation where applicable.

Useful ServiceNow diagnostic tools

  • System Security → Debugging → Debug Security Rules.
  • System Logs → Transactions.
  • System Logs → All.
  • System Definition → Tables.
  • User Administration → Users.
Do not resolve a 403 by granting admin access automatically. Identify the exact table, operation, ACL and required permission first.

08. Connector Diagnostics

Moveworks connectors contain the external system's connection details and authentication configuration.

Diagnostic sequence

  1. Confirm the correct ServiceNow instance URL.
  2. Confirm the correct connector is selected.
  3. Validate authentication configuration.
  4. Check whether credentials have expired or changed.
  5. Review connector test results.
  6. Check Moveworks alerts for integration failures.

Important distinction

A built-in ServiceNow connector and a custom HTTP connector are not necessarily interchangeable. Confirm which integration approach your feature uses before troubleshooting its authentication settings.

09. ServiceNow API Debugging

When a connector reports an API error, isolate the request before investigating the full conversation.

Example: Query a ServiceNow incident

GET /api/now/table/incident

Parameters:
sysparm_query=number=INC0010001
sysparm_fields=number,short_description,state,priority
sysparm_limit=1

Example: Create a diagnostic incident payload

{
  "short_description": "Moveworks integration test",
  "description": "Test incident created in a non-production environment",
  "category": "inquiry"
}

The payload is illustrative. Verify mandatory fields, choice values, table permissions and your instance's business rules before using it.

Example: JavaScript response inspection

function inspectResponse(response) {

    var result = {
        status: response.status,
        success: response.status >= 200 &&
                 response.status < 300
    };

    if (!result.success) {
        gs.error(
            "Integration request failed. HTTP Status: " +
            result.status
        );
    }

    return result;
}
This is a generic response-inspection example, not a drop-in Moveworks Script Include. Do not log passwords, access tokens, personal information or sensitive payloads.

10. Moveworks Alerts

Moveworks Setup includes alerts that can help identify issues affecting integration components.

Alerts worth investigating

Integration Failure

Indicates a system connection failure. Check connector configuration, credentials and authentication.

User Validation Failed

Investigate identity validation and joining-key configuration.

Knowledge Ingestion Failure

Check connector permissions, knowledge ingestion logs and possible ingestion restrictions.

Ticket Filter Alert

Investigate universal ticket fetching filters when tickets are not passing the configured criteria.

Recommended investigation

  1. Open Moveworks Setup Alerts.
  2. Identify the affected integration module.
  3. Review the alert description and downstream impact.
  4. Follow the recommended troubleshooting procedure.
  5. Check the relevant connector or ingestion logs.
  6. Escalate unresolved platform-side issues to Moveworks Support.

11. Advanced Developer Techniques

Technique 1: Compare successful and failed requests

Capture a successful request and a failed request. Compare their endpoint, authentication method, query parameters, response status and execution time.

Technique 2: Test the same request independently

Use an approved REST client to isolate ServiceNow from the Moveworks application flow. If the request works independently but fails through Moveworks, investigate the connector configuration and integration path.

Technique 3: Build a correlation timeline

Record the timestamps of the employee request, Moveworks event, ServiceNow transaction and resulting record update. Use available request or correlation IDs where supported.

Technique 4: Validate permissions with two users

Test with one user who should have access and another who should not. This helps identify permission-mirroring problems without weakening production security.

Technique 5: Test changes in sub-production

Reproduce the issue in a test instance before changing production roles, update sets, ACLs or integration credentials.

Advanced debugging principle: Change one variable at a time, preserve the original error evidence and document the verified result.

12. Production Troubleshooting Checklist

  • ServiceNow instance is reachable.
  • Connector configuration is correct.
  • Authentication succeeds.
  • Integration account is active.
  • Required roles and ACLs are verified.
  • moveworks.base update set is installed.
  • moveworks.acl update set is installed where required.
  • moveworks_user role is assigned.
  • Identity joining keys match.
  • Bot Account fields are validated.
  • Bot Access Rule is configured.
  • Knowledge ingestion is successful.
  • Ticketing and catalog features are tested separately.
  • Unauthorized access is tested.
  • Monitoring and escalation procedures are documented.
