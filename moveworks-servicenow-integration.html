01. Introduction

Moveworks is an enterprise AI platform that helps employees find information, interact with enterprise applications and complete service requests using conversational experiences.

ServiceNow provides the IT service management capabilities behind many enterprise workflows, including incidents, service catalog requests, approvals and knowledge management.

Integrating the two platforms allows employees to interact with supported ServiceNow capabilities through Moveworks.

Moveworks

Conversational AI, enterprise search, employee experience and automation.

ServiceNow

Incident management, service catalog, knowledge management and IT workflows.

Integration

Secure connectivity, identity mapping, data access and supported actions.

02. Integration Architecture

The following is a simplified logical view of the integration. The exact components and data flow depend on the Moveworks product capabilities enabled in your tenant.

Employee

Asks a question or submits a request

↓
Moveworks AI Assistant

Understands intent and selects supported capabilities

↓
Moveworks ServiceNow Connector

Authentication, integration and data exchange

↓
ServiceNow Platform

Incidents, users, catalog items and knowledge

↓
Response to Employee

Supported results or request status

Important architecture distinction: The standard ServiceNow connector, Tool Studio HTTP connectors and ServiceNow MCP integration are different integration approaches. Do not assume their configuration steps or authentication requirements are interchangeable.

03. Prerequisites

Before beginning the integration, collect the required information from both platforms.

ServiceNow requirements

  • Access to the ServiceNow instance.
  • Administrator assistance for update sets and account setup.
  • Integration account with the required roles.
  • ServiceNow instance URL.
  • Integration account email and user ID.
  • Integration account sys_id.
  • Approved authentication and security configuration.

Moveworks requirements

  • Access to Moveworks Setup in your tenant.
  • Permission to configure connectors.
  • Permission to configure user identity.
  • Access to Bot Account and Bot Access settings.
  • Knowledge of the connector naming convention.
Production recommendation: Perform initial setup in a sub-production ServiceNow instance. Follow your organization's change-management and security approval procedures before production rollout.

04. Install ServiceNow Update Sets

For the Moveworks Assistant Platform ServiceNow connection documented in the current setup guide, the required update sets include the base and ACL update sets.

STEP 01

Install moveworks.base

Install the base update set first. It adds the Moveworks application components, including the moveworks_user role.

STEP 02

Install moveworks.acl

Install the ACL update set. This is required for Moveworks to evaluate user criteria on knowledge articles and catalog items.

STEP 03

Preview and Commit

Preview the update sets before committing them. Review any customization collisions with your ServiceNow administrator.

Do not blindly accept update set preview conflicts. Review collisions and their impact on existing customizations before committing.

05. Prepare the Integration Account

Moveworks authenticates to ServiceNow using an integration account. For a shared or production instance, a dedicated account is recommended.

Account preparation

  1. Navigate to User Administration → Users.
  2. Create or identify the integration account.
  3. Assign the required ServiceNow roles.
  4. Assign the Moveworks-specific role.
  5. Populate the account email address.
  6. Set the account time zone to GMT as specified in the setup guide.
  7. Capture the account's 32-character sys_id.

Roles documented for the integration account

  • ITIL
  • Approval Admin
  • Flow Operator
  • Catalog Admin
  • UI Policy Admin
  • Personalize Dictionary
  • moveworks_user
  • snc_basic_auth_api_access
The roles above reflect the documented Assistant Platform setup. Review the current ServiceNow Access Requirements for the exact roles, tables and permissions needed by your enabled capabilities.

Important values to capture

ServiceNow instance URL

https://your-instance.service-now.com

Integration account user ID

your_integration_user

Integration account email

integration@example.com

Integration account sys_id

32-character ServiceNow sys_id
Never publish actual passwords, API secrets, private keys or production sys_ids in a public blog. The values above are examples only.

06. Create the Moveworks Connector

After preparing the ServiceNow integration account, create the ServiceNow connector in Moveworks Setup.

STEP 01

Open Moveworks Setup

Navigate to Connectors → Built-in Connectors.

STEP 02

Select ServiceNow

Choose ServiceNow and start creating the connector.

STEP 03

Enter Connection Details

Enter the ServiceNow instance URL and the integration account credentials required by the connector configuration.

STEP 04

Choose a Connector Name

Use a meaningful name and record it carefully. The connector name cannot be changed after creation in the documented setup flow.

STEP 05

Test the Connection

Run the connector test and confirm that Moveworks can reach ServiceNow successfully.

Do not assume that a successful connection test proves that every feature works. User ingestion, knowledge permissions, forms and ticketing require additional configuration and validation.

07. Configure User Identity Ingestion

User ingestion establishes the relationship between employees in Moveworks and their corresponding ServiceNow user records.

The email address is the default joining key in the documented single-source setup.

STEP 01

Open Identity Configuration

Navigate to User Identity → Identity Configuration.

STEP 02

Select the ServiceNow Connector

Choose the ServiceNow connector as the primary identity source and test its connectivity.

STEP 03

Configure Source Mapping

Review sample users and validate the returned attributes.

Configure the active-user filter: 

active=true
STEP 04

Configure Processors

Add and enable the documented User Timezone Processor and Unified Resolve Manager Processor.

STEP 05

Configure Joining Keys

Confirm that the email address is used as the joining key for the single-source configuration.

STEP 06

Test with a User

Enter your email address and use Show User Profile to validate the identity attributes.

After saving the configuration, check Imported Users. Confirm that your user appears in the roster and that Enabled Users and Bot Reachable Users have valid counts.

08. Configure the Bot Account

The Bot Account configuration connects the Moveworks identity configuration to the ServiceNow integration account.

Navigate to: 

User Identity
  → Advanced Settings
    → Bot Account

Required fields

Email Address

Email configured on the ServiceNow integration account.

Unique Record ID

The joining key value, typically the same email address.

External ID

The integration account's ServiceNow sys_id.

ITSM User ID

The integration account's ServiceNow user ID.

Integration ID

The exact connector name created in the previous step.

These values must match the corresponding ServiceNow integration account and identity configuration. Incorrect values can cause authentication or identity mapping failures.

09. Configure Bot Access

Ingesting a user does not automatically mean that the user is permitted to access the AI Assistant.

STEP 01

Open Bot Access

Navigate to User Identity → Bot Access.

STEP 02

Configure Bot Access Rule

Define which ingested employees can access the Moveworks Assistant.

STEP 03

Choose the Rollout Scope

Use a pilot group or an appropriate access rule for a controlled rollout. Setting the rule to TRUE grants access to all ingested users.

Users also need an enabled access surface, such as an integrated chat platform, My Moveworks or an Embedded AI Assistant.

10. Testing and Validation

After configuration, validate each integration layer independently.

01. Connectivity

Confirm the ServiceNow connector test succeeds.

02. Identity

Confirm users appear in the imported user roster.

03. Bot Account

Verify all Bot Account values match ServiceNow.

04. Access

Confirm the intended pilot users can reach the assistant.

Suggested functional test cases

  1. Search for an accessible knowledge article.
  2. Ask a question about an existing incident.
  3. Test supported incident creation functionality.
  4. Validate user identity mapping.
  5. Test a catalog item after forms are configured.
  6. Verify that unauthorized users cannot access restricted content.
Incident creation, catalog submissions and ticket updates are functional tests for subsequent feature configuration. They are not automatically enabled just by creating the initial connector.

11. Troubleshooting

Use the following table as an initial diagnostic guide. Confirm the actual error message and connector logs before changing configuration.

Connector authentication failure

Possible causes:

  • Incorrect account credentials.
  • Missing API access role.
  • Inactive integration account.
  • Authentication configuration mismatch.

Investigation: Validate account status, roles and connector credentials.

Users missing from Imported Users

Possible causes:

  • Incorrect identity source.
  • Missing or duplicate email addresses.
  • Incorrect source filter.
  • Connector cannot retrieve user records.

Investigation: Validate sample records, email uniqueness and ingestion results.

Bot Account authentication issues

Possible causes:

  • Incorrect integration account email.
  • Incorrect ServiceNow sys_id.
  • Connector name mismatch.
  • Incorrect ITSM user ID.

Investigation: Compare all five Bot Account fields with the actual integration setup.

Knowledge articles not appearing

Possible causes:

  • Knowledge Search is not configured.
  • Knowledge article is not published.
  • Incorrect access or user criteria.
  • Ingestion or indexing has not completed.

Investigation: Check knowledge access, connector permissions and ingestion status.

12. Security Best Practices

  • Use a dedicated integration account for production.
  • Follow least-privilege principles wherever supported.
  • Review update set collisions before committing.
  • Use approved authentication methods.
  • Protect credentials using approved secret-management mechanisms.
  • Validate knowledge and catalog access permissions.
  • Test with authorized and unauthorized user accounts.
  • Monitor integration activity and authentication failures.
  • Follow enterprise change-management requirements.
