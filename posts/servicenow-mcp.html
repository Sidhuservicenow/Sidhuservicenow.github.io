Model Context Protocol (MCP) with ServiceNow: Tools, Architecture, Security, and Implementation

Model Context Protocol (MCP) provides a standardized way for AI applications to discover and interact with external capabilities. For ServiceNow developers, MCP creates a practical interoperability layer between AI clients and governed ServiceNow tools, data, and workflows.

September 2026 · 18 min read · MCP · ServiceNow AI · Agentic AI
Architecture in one sentence: An AI application acts as the MCP client, connects to an MCP server, discovers the server's available capabilities, and invokes approved ServiceNow tools through a standardized protocol.

1. What is MCP?

Model Context Protocol, commonly called MCP, is an open standard for connecting AI applications to systems where useful data and actions live. Instead of building a different AI-specific integration for every client and every enterprise system, MCP defines a common interaction model.

The protocol separates the AI application from the system that exposes the capability. An AI host can connect through an MCP client to an MCP server, and the server exposes capabilities that the client can discover and use.

The current MCP specification defines core server primitives including tools, resources, and prompts. Tools are executable functions, resources provide contextual data, and prompts are reusable interaction templates.

The basic MCP model
AI Application / Host
↓
MCP Client
↓
MCP Protocol
↓
MCP Server
↓
Tools / Resources / Prompts
↓
ServiceNow APIs, workflows, records, or platform capabilities

2. Why should a ServiceNow developer care?

Traditional integrations often create a point-to-point relationship between an AI application and a ServiceNow API. As the number of AI clients grows, the integration surface can grow with it.

MCP changes the integration boundary. Instead of asking every AI client to understand ServiceNow-specific endpoints, the MCP server exposes a curated set of capabilities using a common protocol.

Traditional point-to-point integration MCP-based integration
Client is tightly coupled to API details. Client discovers standardized capabilities.
Each AI client may require custom integration code. Multiple compatible clients can use the same MCP server.
Tool descriptions may be duplicated across clients. Capabilities can be published by the server.
Governance is often implemented separately for each connector. Governance can be centralized around the server and its tools.

MCP does not eliminate APIs. A ServiceNow MCP implementation can still use platform APIs, Scripted REST APIs, actions, subflows, or other server-side mechanisms underneath the MCP tool.

3. MCP is not a replacement for REST APIs

This distinction is important. REST APIs describe how software communicates with a service. MCP describes a standardized way for AI applications to discover and use capabilities exposed by an MCP server.

AI Client | | MCP v MCP Server | | ServiceNow API / Flow / Action / Script v ServiceNow Platform

In other words, MCP can sit above existing ServiceNow integration capabilities rather than replacing them.

4. The three important MCP primitives

Tools

Tools are executable operations. They are the most important primitive when an AI application needs to perform an action or retrieve information through a defined function.

ServiceNow-oriented examples could include:

  • Find an incident.
  • Get details for a change request.
  • Search approved knowledge.
  • Check the assignment group for an incident.
  • Create a request using an approved workflow.
  • Trigger a controlled automation.

Resources

Resources represent contextual information that an MCP client can use. Depending on the implementation, resources can represent documents, records, configuration information, or other structured content.

Prompts

Prompts are reusable templates or instructions exposed by an MCP server. They can provide a consistent way to initiate a particular interaction.

Developer mental model: Think of tools as things the AI can call, resources as information it can access, and prompts as reusable interaction patterns.

5. ServiceNow as an MCP server

ServiceNow provides MCP capabilities through its MCP Server Console and related platform features. The ServiceNow approach focuses on exposing selected platform capabilities as governed MCP tools rather than simply opening generic database access to an AI client.

ServiceNow has also expanded its MCP capabilities over time, including prebuilt and domain-oriented server options. Availability and exact capabilities depend on the ServiceNow release, plugins, licensing, and configuration in the target environment.

ServiceNow as the governed MCP server
External AI Client / Agent

↓
Curated MCP Tool Catalog
↓
ServiceNow Actions / Subflows / Skills / APIs
↓
ServiceNow Data and Business Workflows

6. ServiceNow can also act as an MCP client

MCP is not limited to the pattern where ServiceNow is the server. ServiceNow can also connect to external MCP servers so that AI agents or platform capabilities can use tools hosted outside the ServiceNow instance.

This creates two useful enterprise patterns:

  1. ServiceNow as MCP server: external AI clients use governed ServiceNow capabilities.
  2. ServiceNow as MCP client: ServiceNow AI capabilities consume approved tools exposed by external MCP servers.
Pattern A External AI ↓ MCP Client ↓ ServiceNow MCP Server ↓ ServiceNow Pattern B ServiceNow AI Agent ↓ MCP Client ↓ External MCP Server ↓ External Tool / Data

7. How tool discovery works

One of MCP's important characteristics is capability discovery. A client does not necessarily need every tool's implementation details hard-coded into the application.

The server publishes information about available capabilities. The client can discover the available tools and their input requirements, then use an appropriate tool when the AI workflow determines that it is needed.

Conceptual example

MCP server publishes: Tool: find_incident Description: Find an incident by number. Input: { "incident_number": "string" } Tool: create_incident Description: Create an incident using an approved workflow. Input: { "short_description": "string", "description": "string" }

The important part is that the tool contract describes the capability. The server remains responsible for implementing the actual operation.

8. Designing a good ServiceNow MCP tool

The quality of an MCP implementation depends heavily on the quality of its tools. A tool should represent a useful business capability rather than exposing an unnecessarily low-level database operation.

Prefer business actions

Good: get_incident_summary find_open_incidents create_access_request check_change_status Less useful as a first abstraction: query_table update_any_record delete_record run_arbitrary_script

A purpose-built tool can apply validation, business rules, authorization, and domain-specific logic before performing the underlying operation.

Design principle: Give the AI the smallest useful capability that can safely accomplish the business task. Avoid turning MCP into unrestricted database access.

9. MCP tool implementation pattern

A ServiceNow MCP tool can conceptually delegate to an existing server-side capability instead of implementing all business logic inside the MCP layer.

MCP Tool ↓ Validation ↓ Authorization ↓ ServiceNow Action / Subflow / Script Include ↓ Business Logic ↓ Approved Data ↓ Structured MCP Result

This architecture makes MCP another controlled interface to the platform rather than a second location where business logic has to be recreated.

10. Security is the most important part

MCP can increase the number of actions an AI system can reach. That is useful, but it also increases the importance of authorization, input validation, tool design, auditability, and data protection.

A tool that can read a record has a different risk profile from a tool that can delete data or approve a request. Tool design should therefore account for the consequences of each operation.

  • Authenticate the MCP client.
  • Authorize access to the MCP server.
  • Control which users or agents can discover each tool.
  • Enforce ServiceNow roles and ACLs.
  • Validate every tool argument server-side.
  • Use least-privilege access for machine identities.
  • Separate read operations from high-impact write operations.
  • Log important tool invocations for audit and troubleshooting.
  • Protect sensitive data from unnecessary model exposure.
  • Consider approval or human confirmation for high-impact actions.

11. Why generic CRUD tools can be dangerous

It may be technically convenient to expose generic create, read, update, and delete operations against a broad ServiceNow table. But an AI system with a generic write capability can become difficult to constrain.

A more controlled approach is to expose task-specific tools. For example, instead of giving an agent an unrestricted update operation, expose a specific action such as assign_incident with an explicit schema and server-side validation.

Generic: update_record(table, sys_id, fields) Controlled: assign_incident( incident_number, assignment_group )

The second pattern gives the server a clearer place to enforce what the AI is allowed to change.

12. MCP and ServiceNow AI Agents

MCP becomes especially interesting when combined with AI agents. An agent can reason about a task, identify a required capability, select a tool, provide the tool inputs, receive the result, and continue the workflow.

13. MCP vs custom REST integration

MCP and REST are not competing technologies. The right choice depends on the integration boundary and the consumers of the capability.

Scenario Typical pattern
A known application needs a deterministic API contract. REST API
Multiple AI clients need standardized tool discovery. MCP
A ServiceNow workflow needs to call another enterprise API. REST / IntegrationHub / Flow Designer
An AI agent needs governed access to multiple capabilities. MCP can provide the tool interface

14. MCP and IntegrationHub

IntegrationHub and MCP solve different layers of the problem.

IntegrationHub can orchestrate integrations and actions across enterprise systems. MCP provides a standardized interface through which AI clients can discover and invoke selected capabilities.

AI Client ↓ MCP Tool ↓ ServiceNow Action ↓ IntegrationHub ↓ External Enterprise System

This combination allows the AI-facing interface to remain focused on a controlled business capability while the underlying workflow continues to use ServiceNow's integration tooling.

15. MCP and RAG

MCP and retrieval-augmented generation are complementary.

RAG focuses on retrieving relevant information for the model. MCP focuses on standardized interaction between an AI application and external capabilities.

User question ↓ AI Agent ↓ MCP tool → retrieve approved ServiceNow knowledge ↓ Relevant context ↓ Model reasoning ↓ Answer or next tool call

A mature enterprise architecture can therefore use MCP as the tool interoperability layer while using retrieval systems to provide relevant enterprise context.

16. MCP and the 2026 protocol evolution

MCP is evolving quickly. The 2026-07-28 specification introduced a stateless protocol core, additional authorization hardening, cacheable list results, an extensions framework, and changes around long-running tasks and transports.

This matters for developers because MCP implementations should avoid assuming that older transport or session behavior will remain the long-term standard. When building production systems, target the protocol version supported by the client, server, and SDKs you actually deploy.

Practical rule: MCP specifications and ServiceNow capabilities are evolving independently. Always verify the supported MCP revision, ServiceNow release, plugin/version, authentication method, and client compatibility before implementing a production integration.

17. A practical ServiceNow MCP project

A good first project is an Incident MCP Server with a small, carefully selected tool catalog.

Example tool catalog

find_incident get_incident_summary get_incident_work_notes get_assignment_group create_incident

Start with read-only capabilities. After authorization, validation, and auditing are established, carefully introduce write operations.

Example request flow

User ↓ AI Client ↓ MCP Client ↓ ServiceNow MCP Server ↓ find_incident ↓ ServiceNow server-side logic ↓ ACL / authorization check ↓ Incident data ↓ MCP result ↓ AI response

18. Testing an MCP implementation

MCP testing should cover more than whether a tool returns the expected result. The security boundary is equally important.

  • Can an authorized client discover the intended tools?
  • Can an unauthorized client connect?
  • Can a user call a tool they should not access?
  • Are invalid arguments rejected?
  • Are high-impact operations protected?
  • Does the tool return predictable structured output?
  • Are errors safe and useful?
  • Are tool calls auditable?
  • Is sensitive data minimized?
  • Does the implementation behave correctly after client/server upgrades?

19. Common MCP mistakes

  • Treating MCP as a replacement for all existing APIs.
  • Exposing broad generic CRUD operations without strong controls.
  • Allowing the AI to bypass ServiceNow authorization.
  • Putting business logic only in the MCP layer instead of reusable server-side services.
  • Giving every agent access to every tool.
  • Ignoring the difference between read and write capabilities.
  • Logging sensitive tool payloads unnecessarily.
  • Assuming protocol behavior from an older MCP specification.
  • Building tools around database tables instead of business outcomes.
  • Skipping negative security tests.

21. Developer checklist

  • Define the business capability before creating the MCP tool.
  • Choose whether ServiceNow is the MCP client, server, or both.
  • Keep tools small, explicit, and purpose-built.
  • Reuse existing ServiceNow business logic where possible.
  • Apply authentication and authorization before tool execution.
  • Validate every input on the server.
  • Separate read and write capabilities.
  • Use least-privilege identities.
  • Define audit and observability requirements.
  • Test unauthorized and malformed requests.
  • Verify ServiceNow release and MCP protocol compatibility.
  • Document every exposed tool and its intended audience.

22. Final mental model

For a ServiceNow developer, the simplest way to think about MCP is as an interoperability layer between AI applications and enterprise capabilities.

AI │ │ understands the task ▼ MCP Client │ │ discovers / calls capabilities ▼ MCP Server │ │ exposes governed tools ▼ ServiceNow │ ├── Actions ├── Subflows ├── APIs ├── Knowledge ├── Records └── Workflows

The key is not simply making ServiceNow callable by AI. The real engineering work is deciding which capabilities should be exposed, how they are authorized, what data they can access, how results are validated, and how every action is governed and observed.

That is what turns MCP from a protocol experiment into an enterprise architecture pattern.
