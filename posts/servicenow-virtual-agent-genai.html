ServiceNow Virtual Agent + Generative AI: Architecture, LLM Topics, Knowledge, and Implementation

ServiceNow Virtual Agent provides a conversational interface for self-service. Generative AI extends that experience by allowing conversations to understand natural language more flexibly, retrieve relevant enterprise context, and connect conversations to platform actions and workflows.

September 2026 · 18 min read · Virtual Agent · Generative AI · ServiceNow AI
Architecture in one sentence: Use Virtual Agent as the conversational experience, combine deterministic topics and LLM-powered experiences where appropriate, ground answers in approved enterprise context, and keep business actions behind governed ServiceNow capabilities.

1. What is ServiceNow Virtual Agent?

ServiceNow Virtual Agent (VA) is a conversational self-service experience that allows employees, customers, and other users to interact with ServiceNow through natural-language conversations.

Traditional Virtual Agent implementations can use topics, conversation flows, NLU models, input collection, decision logic, and actions. The conversation can then retrieve information or invoke ServiceNow workflows instead of requiring the user to navigate multiple forms and applications.

The important developer idea is that Virtual Agent is not just a chatbot UI. It is a conversational entry point into platform capabilities.

Traditional Virtual Agent mental model
User message
↓
Intent / topic discovery
↓
Topic conversation and input collection
↓
ServiceNow action / Flow / API
↓
Result returned to the user

2. Where Generative AI changes the experience

Generative AI changes the interaction model from conversations that depend heavily on predefined paths toward conversations that can interpret broader natural-language requests and generate responses from available context.

ServiceNow's Now Assist in Virtual Agent provides generative AI capabilities for conversational experiences. ServiceNow has also introduced LLM-powered Virtual Agent topics that can create natural-language conversations without relying on traditional NLU topic matching in the same way.

This does not mean every conversation should become fully generative. Deterministic flows remain useful when the business process requires exact inputs, predictable branching, validation, approvals, or tightly controlled execution.

Pattern Strength Typical use
Deterministic VA topic Predictable process control Structured requests, approvals, known workflows
NLU-based experience Intent classification Known user intents mapped to topics
LLM-powered topic Natural-language interaction and flexible input collection Conversational requests with varied wording
Generative answer / search Contextual answers from enterprise knowledge Questions where the user needs information rather than a transaction

3. Virtual Agent + Now Assist

Now Assist is ServiceNow's family of generative AI experiences. In the Virtual Agent context, generative AI can be used to provide more conversational answers, support natural-language interactions, and connect users to relevant information and workflows.

ServiceNow has described Now Assist for Virtual Agent as a low-code generative AI capability that can provide direct answers, use enterprise context, and connect conversations to digital workflows.

4. NLU versus LLM-powered conversations

Natural Language Understanding (NLU) and large language models solve related but different problems.

An NLU-oriented design commonly maps user language to a known intent or topic. The topic then follows a predefined conversational flow.

An LLM-powered design can interpret a broader range of language and can perform tasks such as extracting inputs from a user's natural-language message or generating a response based on provided context.

NLU-oriented User message ↓ Intent classification ↓ Known topic ↓ Predefined conversation ↓ Action LLM-powered User message ↓ LLM interprets intent + context ↓ LLM-powered topic / skill ↓ Input extraction or response generation ↓ Action / retrieval / response

In practice, these patterns can coexist. A production ServiceNow environment can use deterministic topics for critical processes while using generative experiences for flexible questions and conversational input.

5. LLM-powered Virtual Agent topics

ServiceNow documentation and product material describe LLM-powered Virtual Agent topics that can create natural-language conversations without requiring the same traditional NLU approach.

One useful capability is natural-language input collection. Instead of forcing a user to answer every question in a rigid sequence, the LLM can interpret a user utterance and populate relevant inputs when the topic is configured to request those values.

For example, an application troubleshooting conversation might need the application name, problem description, and priority. A user could provide several of those details in one natural-language message instead of answering every field independently.

User: "My VPN stopped connecting after I changed my password. I need this fixed urgently." Potential extracted context: - Application / service: VPN - Issue: connection failure - Priority signal: urgent Topic: - Validate required information - Ask only for missing information - Invoke the appropriate ServiceNow action - Return the result
Important: Natural-language input extraction should not automatically equal authorization. The server-side workflow must still validate the actual user, requested action, required fields, and permissions.

6. Where knowledge retrieval fits

Many Virtual Agent conversations are information-seeking questions: "How do I reset my password?", "What is the VPN policy?", or "What is the process for requesting a laptop?"

These scenarios benefit from grounding the generated response in approved enterprise knowledge rather than asking the model to answer from general knowledge alone.

ServiceNow supports AI-powered search experiences that can retrieve relevant knowledge and generate concise answers. The exact features available depend on the ServiceNow release, products, licensing, and configuration.

Grounded conversational answer
User question
↓

↓
Retrieve relevant approved knowledge
↓
Apply user / access context
↓
Generate grounded answer
↓
Show answer with appropriate source / next action

7. Knowledge quality becomes an AI engineering concern

A generative conversational experience can only be as useful as the information it is allowed to retrieve and use. Outdated, duplicate, contradictory, or poorly written knowledge can produce poor answers even when the model itself is working as designed.

ServiceNow guidance also emphasizes the possibility of inaccurate or irrelevant generated content. Developers should therefore treat knowledge governance as part of the AI architecture.

  • Define ownership for important knowledge bases.
  • Review outdated articles and duplicate content.
  • Use clear article titles and useful content structure.
  • Apply appropriate user criteria and access controls.
  • Test retrieval using real employee questions.
  • Monitor unanswered and poorly answered questions.
  • Keep source content aligned with current business processes.

8. Virtual Agent can do more than answer questions

The strongest enterprise conversational experiences connect conversation to action. A user may start with a question but eventually need ServiceNow to perform a task.

Examples include:

  • Create an incident.
  • Check incident status.
  • Request software.
  • Order a catalog item.
  • Reset or unlock an account through an approved workflow.
  • Check an HR request.
  • Start a facilities request.
  • Route a complex issue to a human support team.
Question ↓ Understand request ↓ Retrieve context ↓ Determine whether action is required ↓ Validate inputs + authorization ↓ ServiceNow Flow / Action / API ↓ Result ↓ Conversational response

9. Catalog ordering through conversational experiences

ServiceNow has also introduced conversational catalog experiences in its Virtual Agent and Now Assist ecosystem. This is an important pattern because a conversational request can be transformed into structured catalog input.

From a developer perspective, the important boundary is between language interpretation and transaction execution. The conversational layer can collect or infer information, but the underlying catalog and platform controls still need to validate the request.

Developer rule: Treat conversationally collected values as untrusted input until the server-side application, catalog, policy, and authorization layers validate them.

11. Keep the model away from unrestricted business operations

A common architectural mistake is to let the conversational model directly decide how database records should be changed. A safer pattern is to place explicit ServiceNow capabilities between the model and the business data.

Less controlled User ↓ LLM ↓ Generic record update ↓ Database More controlled User ↓ Virtual Agent / LLM ↓ Approved business action ↓ Validation + authorization ↓ Flow / Action / Script Include ↓ ServiceNow data

This gives developers a clear place to enforce business rules, ACLs, validation, approvals, and logging.

12. Virtual Agent + Flow Designer

Flow Designer is a natural execution layer for conversational actions. Virtual Agent can collect the user's intent and required inputs, while a flow or action handles the deterministic business process.

Virtual Agent ↓ Collect / validate inputs ↓ Flow Designer Action ↓ Subflow ↓ Business rules / approvals ↓ Integration or record operation ↓ Return status ↓ Virtual Agent response

This separation also makes the implementation easier to test. The business flow can be tested independently of the conversational interface.

13. Virtual Agent + AI Agents

Conversational experiences can also become an entry point into more agentic workflows. In such an architecture, Virtual Agent handles the user interaction while an AI Agent or agentic workflow can select tools and coordinate multiple steps.

From conversation to agentic workflow
User request
↓
Virtual Agent / Now Assist
↓
AI Agent / orchestration
↓
Skills / tools / ServiceNow capabilities
↓
Workflow + enterprise systems
↓
Result + human review where appropriate

The key design principle is that conversational intelligence and business execution remain separate layers. This makes the architecture easier to govern as the system becomes more capable.

14. Security and access control

Generative AI does not remove ServiceNow's existing security responsibilities. A conversational experience must still respect the user's identity, permissions, data access, and business policies.

  • Authenticate the user through the supported experience.
  • Respect roles, ACLs, and user criteria.
  • Do not expose knowledge that the user is not authorized to access.
  • Validate action inputs server-side.
  • Use least privilege for integrations and machine identities.
  • Protect secrets and credentials from prompts and client-side code.
  • Minimize sensitive data sent to external AI services.
  • Log operational events without unnecessarily storing sensitive conversation content.
  • Require confirmation or human approval for high-impact actions when appropriate.

15. Prompt injection and untrusted content

Enterprise conversational AI must also consider prompt injection. User messages, knowledge articles, external content, and retrieved text should not automatically be treated as trusted instructions.

A useful mental model is to distinguish between instructions and data. Retrieved content should provide context for the response, not silently override system-level controls or authorization.

Practical rule: Never use a user's natural-language request as the sole authorization for a privileged operation. Authorization belongs in the application and platform security layers.

16. Human escalation is part of the architecture

Not every request should end with an AI-generated answer. A mature conversational experience needs a clear path to a human agent when the system cannot confidently resolve the request or when policy requires human involvement.

Useful escalation signals include:

  • The requested operation is outside the assistant's scope.
  • Required information is missing or contradictory.
  • The user disputes the generated answer.
  • The operation has significant business impact.
  • The system cannot retrieve an appropriate source.
  • Repeated attempts fail to resolve the request.

17. Observability and testing

Testing a generative conversational experience requires more than checking whether the chat window opens. Developers should test the complete path from user utterance through retrieval, reasoning, action execution, and response.

  • Test common user wording variations.
  • Test incomplete requests.
  • Test ambiguous requests.
  • Test unauthorized requests.
  • Test prompt injection attempts.
  • Test knowledge retrieval quality.
  • Test incorrect or outdated knowledge.
  • Test workflow failures and timeouts.
  • Test escalation to human support.
  • Measure latency and operational errors.
  • Review generated answers for factual grounding.

18. Common implementation mistakes

  • Making everything generative: deterministic workflows are still valuable for controlled transactions.
  • Ignoring knowledge quality: poor source content can produce poor grounded answers.
  • Trusting extracted values: LLM-extracted inputs still require validation.
  • Bypassing platform security: conversational AI should not create a new path around ACLs or roles.
  • Putting credentials in client-side code: secrets belong in secure server-side configuration.
  • Using unrestricted record operations: prefer narrowly scoped business actions.
  • No human fallback: users need a path out when AI cannot safely resolve the issue.
  • Testing only happy paths: failure and security scenarios are critical.
  • Ignoring licensing and release differences: verify the exact capabilities available in the target instance.

19. A practical project: Employee IT Help Assistant

A useful first project is an employee IT help assistant that combines knowledge retrieval with a small set of controlled actions.

Example capabilities

Knowledge: - Password reset instructions - VPN troubleshooting - Laptop setup - Software request policy Actions: - Check incident status - Create incident - Submit software request - Escalate to support

Example conversation

User: "My VPN is not connecting. I already restarted my laptop." Assistant: 1. Understand the issue. 2. Retrieve approved VPN troubleshooting guidance. 3. Provide the relevant steps. 4. Ask whether the issue remains. 5. If required, collect the information needed to create an incident. 6. Invoke the approved incident action. 7. Return the incident number. Result: Conversation → knowledge → action → workflow → result

20. Developer implementation checklist

  • Define the business use case.
  • Decide which conversations should be deterministic.
  • Identify where LLM-powered interaction adds value.
  • Review and clean the source knowledge.
  • Define the required user context.
  • Design approved actions and flows.
  • Apply ACLs, roles, user criteria, and authorization checks.
  • Validate every important input server-side.
  • Design escalation and human handoff.
  • Test hallucination, injection, security, and failure scenarios.
  • Measure response quality, latency, and operational errors.
  • Verify the target ServiceNow release, plugins, licensing, and supported AI capabilities.

21. Final architecture

USER | v Employee Center / Portal / Teams | v VIRTUAL AGENT | +-------------+-------------+ | | | v v v Deterministic LLM Topic AI Search / Topic / Skill Knowledge | | | +-------------+-------------+ | v Context + Security | +-----------+-----------+ | | v v Generated Answer Approved Action | v Flow / Action / API | v ServiceNow / Enterprise | v Result + Audit | v User Response

The most useful way to think about Virtual Agent + Generative AI is not "replace the chatbot with an LLM." It is to build a conversational layer that can understand natural language while still relying on governed enterprise data, deterministic workflows, platform security, and human escalation.

That separation is what makes the architecture maintainable. The model can improve over time without forcing every business process to become an uncontrolled generative workflow.
